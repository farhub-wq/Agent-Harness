# 数据库迁移

这个目录里的每个 `.js` 文件是一次**只前进**的结构变更。执行器是
[`deploy/dr/migrate.sh`](../deploy/dr/migrate.sh)，由
[`deploy/cd/deploy.sh`](../deploy/cd/deploy.sh) 在**备份之后、同步源码树之前**调用。

它跑在同步之前，是因为迁移失败时的语义应该是「生产一个字节都没动过」——
与备份失败（退出码 2）同级，所以它有独立的退出码 **8**。代价是迁移必须从
**新 commit** 里取（`git archive`），不能读生产树里那份（那时还是旧版）。

## 硬规则

### 1. 文件名就是编号，四位递增，不复用、不重排

`0001_baseline.js` → `0002_add_xxx.js` → …

编号是账本 `schema_version` 的主键。改一个已应用迁移的**文件名**等于让账本指向
一个不存在的编号，执行器会告警；改它的**内容**会直接失败（见规则 3）。

### 2. 只前进

没有 down 迁移，也没有 `--rollback`。回滚数据库靠
[`deploy/dr/backup.sh`](../deploy/dr/backup.sh) 的备份，不靠 undo 脚本。

理由不是"懒得写"：undo 脚本只有**被验证过**才可信，而验证它的唯一办法是真的
滚一遍 —— 那等于把发布流程的复杂度翻一倍，去换一个备份已经提供的东西。而一个
没被验证过的 undo 脚本，在真需要它的那一刻会表现得和"没有"一样，只是更费时间。

### 3. 已应用的迁移是只读历史

执行器把每个文件跑完时的 sha256 记进账本。下次再看到同一个编号但哈希不同，
它会**失败并停住**，不执行任何迁移。数据库现在的形状是按旧内容来的，账本说它
是新的 —— 之后所有判断都建在一个错的前提上。

要改结构？新加一个编号。

### 4. 每个迁移必须对**上一版**代码向后兼容

这一条最容易违反，也最难在事后补救。因为执行顺序是：

```
备份 → 【迁移】 → 同步新代码 → 影子启动 → 换版
```

迁移跑完的那一瞬间，**正在服务用户的仍然是旧代码**。旧代码还会在这个新结构上
跑几分钟到几十分钟（影子启动 + 换版 + 观察窗）。所以：

| 可以做 | 不能做 |
|---|---|
| 加集合、加索引、加字段 | 删集合、删字段、删索引 |
| 加字段时给出默认值 | 把某个字段改成必填 |
| 老字段和新字段并存、双写 | 把字段改名、改类型、改语义 |
| 回填数据（小批量） | 用新结构的**语义**去解释旧字段 |

删除属于**下一次**发布：先在 N 版里把代码改成不再依赖它，等 N 版稳定运行过，
再在 N+1 版里发一个迁移删掉它。这就是 expand / contract。

### 5. 必须幂等

「跑完了但记账没写进去」是可能的（进程被杀、容器重启）。执行器已经把迁移执行
和记账拆成两次往返，但断在中间仍然会发生，而这时下一次发布会**重跑**它。

写法上就是：`createIndex` 而不是先 `dropIndex` 再 `createIndex`；插入前先查；
`$set` 而不是 `$setOnInsert` 之外的覆盖写。

### 6. 不要在这个目录里建业务数据

迁移管的是**结构**：集合、索引、约束。需要写业务数据的（比如给所有会话补一个
字段的初始值）要单独评审 —— 它会在发布路径上持锁，而 2 核 / 3.6G 的机器上
一次大范围 `updateMany` 足够让发布超时。

大批量回填应该是一个能断点续跑、可以单独调的脚本，不是发布路径上的一步。

### 7. 不要把这些库自带的集合写进迁移

`checkpointing_db` 的 `checkpoints` / `checkpoint_writes` 的索引是
langgraph-checkpoint-mongodb **自己建的**。把它们复制进来，一旦库升级改了索引
定义，迁移器和库就会各建一个 spec 不同的同名索引 —— `IndexOptionsConflict`，
而且是在发布路径上炸。

## 库名从哪来

迁移脚本里用 `process.env.MONGODB_DB_NAME` 取应用库名，**不要写死 `erp_agent`**。
这个变量由 compose 的 `env_file: ./deploy/.env` 注入 mongo 容器，与应用代码读的
是同一个值。

注意这与 [`deploy/dr/backup.sh`](../deploy/dr/backup.sh) 里"库清单必须运行时
枚举、不信配置"的决定看起来相反，但两处面对的是不同的问题：备份要发现的是
**配置里根本没有的那个库**（`checkpointing_db` 是 langgraph 的库默认值，不出现在
任何配置里），而迁移要的正是应用配置里那一个。

## 账本

应用库（`MONGODB_DB_NAME`）里的 `schema_version` 集合：

```js
{ _id: "0001", checksum: "<文件 sha256>", applied_at: ISODate(...), host: "..." }
```

放在应用库里是刻意的：备份是逐库 dump + 恢复自检的，账本跟着数据一起被备份、
一起被回滚。放到别的库里的话，从一份旧备份恢复之后，账本会记着"迁移都已应用"
而实际数据是旧结构 —— 那是最糟的一种不一致。

## 怎么用

```bash
# 看现在什么状态（不碰数据库）
bash deploy/dr/migrate.sh --dir migrations --status

# 演练：列出将要执行什么，不执行
bash deploy/dr/migrate.sh --dir migrations --dry-run

# 真的执行（本地目录）
bash deploy/dr/migrate.sh --dir migrations

# 发布路径上的形态：从新 commit 取（生产树这时还是旧版）
bash deploy/dr/migrate.sh --sha <40位commit>
```

本地能连到生产 mongo 的场景不存在（端口没有对外发布，见 `docker-compose.yml`），
所以 `--dir` 是给开发机/CI 用的，生产上一律走 `--sha`。

## 新增一个迁移

1. 建 `migrations/000N_描述.js`，用上一条的规则自查一遍（尤其是规则 4）
2. 在 `deploy/ci/backup-dr.sh` 同级的 CI 里跑一遍 —— 迁移路径每次 PR 都会被真的
   执行一次（见 `.github/workflows/_gates.yml`），不会等到发布才发现
3. 本地：`bash deploy/ci/dr-logic-test.sh`（纯逻辑）与
   `bash deploy/dr/migrate.sh --dir migrations --dry-run`（清单）
